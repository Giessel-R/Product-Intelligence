Architecture Quirks

Non-obvious rules that govern how this system is built. Each one was discovered the hard way — through failed test runs, broken nodes, or silent data loss. Read these before modifying any workflow.

warning
These are live constraints
These rules reflect real bugs and limitations in n8n's runtime. Violating them will cause silent failures, data loss, or broken workflows that appear to succeed.
1
Orchestrator IF nodes
Master Orchestrator
Always reference $('Initialize Run').first().json — never $json. In the Orchestrator, $json reflects the output of the most recently executed node, which changes as sub-workflows return. The day-of-week flags (is_monday, is_tue_thu, is_friday) are set once at the start in Initialize Run and must be read from that specific node.
2
Notion node v2.2 rich_text bug
Newsletter
The n8n Notion node (v2.2) is broken for rich_text properties — it silently discards content. Use an HTTP Request node instead: POST https://api.notion.com/v1/pages with predefinedCredentialType: notionApi. Never use the built-in Notion node for writing rich text blocks.
3
HTTP Request raw body format
All HTTP Request nodes
Use contentType: "raw" paired with rawContentType: "application/json" and body: "={{ JSON.stringify({...}) }}". Do not use "rawBody" as the key — it is not a valid field and will be silently ignored, sending an empty body.
4
Code node sandbox blocks HTTP
All Code nodes
fetch and $helpers.httpRequest are both blocked in n8n's Code node sandbox. Any HTTP call must use a dedicated HTTP Request node — a Code node cannot make network requests.
5
$env blocked in HTTP Request headers
Anthropic HTTP calls
Environment variables ($env.MY_KEY) are blocked in HTTP Request node header fields. For Anthropic API calls, use predefinedCredentialType: httpHeaderAuth with credential ID P6dgBaH33wjoGxqb — the API key is stored securely in n8n's credential vault.
6
Sub-workflows cannot be tested via API
All sub-workflows
Sub-workflows (Market Watch, IPS, CI, Newsletter, Memory & Audit, Error Handler) all use executeWorkflowTrigger as their entry point. The n8n_test_workflow API tool cannot trigger this node type — it only works with webhooks and schedules. Test sub-workflows manually in the n8n UI by running them directly.
7
n8n_update_full_workflow requires name
n8n API
The n8n_update_full_workflow API call requires the name field to be present in the request body — even if you are not changing the workflow name. Omitting it returns a validation error. Always include the current workflow name when using this tool.
8
n8n_update_partial_workflow cannot update nested arrays
n8n API
n8n_update_partial_workflow cannot update nested array items — for example, changing conditions[0].leftValue in an IF node. Use n8n_update_full_workflow for any change that touches condition arrays, parameters arrays, or any nested structure.
9
Chain resilience pattern
Master Orchestrator
Every executeWorkflow node must have continueOnFail: true AND be followed by a guard Code node. The guard emits a synthetic { status: "success" } item if the sub-workflow returned 0 items — preventing the chain from silently halting. The guard must be wired as a connection — a Code node with 0 items flowing in never executes.
10
CI evidence cutoff: 3 days
Competitor Intelligence
Competitor Intelligence reads only evidence from the last 3 days from evidence_log. If the schedule is missed (e.g., a Tuesday run is skipped), that day's evidence is not recovered on Thursday. Consistent scheduling is required to avoid evidence gaps. The cutoff exists to prevent CI from reprocessing stale findings.
