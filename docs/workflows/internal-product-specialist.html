Internal Product Specialist

The "know yourself" workflow. Reads Ping's own documentation every Monday to build a capability map: the source of truth used by Competitor Intelligence to identify genuine gaps vs. parity.

Workflow ID63fbsmdUxNtnaFXG
Triggered byMaster Orchestrator · Mondays only
AI modelClaude Sonnet: nuanced capability extraction
Writes tointernal_capability_map (Google Sheets)
Reads fromsource_registry tab (Google Sheets): active rows filtered by P1/P2/P3 cadence
info How It Works

Before the system can say "Okta has X that Ping doesn't have," it needs to know what Ping has. IPS reads Ping sources every Monday: pulling from the source_registry tab in Google Sheets (80+ active sources): and asks Claude Sonnet: "What capabilities does this document? Be specific. Only include things clearly supported."

Stage 5 replaced the old hardcoded Define Ping Sources node with a live read from source_registry. Sources are staggered by priority cadence: P1 runs every Monday, P2 every other week, P3 once a month. New sources discovered by the Source Discovery workflow enter as candidate and must be promoted to active before IPS picks them up.

Stage 2 added parser safety caps: sample_app sources are hard-capped at sample_only maturity regardless of Claude's output. github_repo sources cannot return production_mature without strong release or version signals. When a cap fires, [parser-cap] is prefixed to the maturity_reason field: Claude's original value is not stored.

The result: each Monday, internal_capability_map is rebuilt with a precise, source-calibrated picture of Ping's capabilities across all 6 strategic lanes. The sheet is cleared at the start of every run: if it is empty, IPS has not run yet this week or found no qualifying capabilities.

info
Support Maturity Vocabulary
Always use these exact values: no others: production_mature | documented | partial | unclear | sample_only. Source type determines the ceiling: sample_app → hard cap at sample_only, confidence ≤ 3. github_repo → cannot return production_mature unless strong release/version signals. release_notes → supports production_mature.

executeWorkflowTrigger
Entry point when launched by the Master Orchestrator. Receives the run_id for this session. Cannot be tested via n8n_test_workflow: must be triggered manually in the n8n UI for isolated testing.
2
Set Run Context
Set
Sets the run ID, current week, and timestamp for this session. Used to stamp all capability rows with their extraction date.
3
Read Source Registry
Google Sheets
Reads the source_registry tab from Google Sheets. Only rows with status = active are used. This replaced the old hardcoded Define Ping Sources Code node in Stage 5. The registry currently holds 80+ sources; new discoveries from Source Discovery enter as candidate until promoted.
4
Filter by Priority Cadence
Code
Applies P1/P2/P3 priority logic based on the ISO week number. P1 sources run every Monday. P2 sources run every other week. P3 sources run once a month. This staggers the workload so the workflow doesn't fetch every source on every run. NARROW_TEST_LANE is null (full-lane operation active): set to a lane string only for targeted testing.
5
Split to Individual Sources
Split Out
Splits the filtered source list into individual items for per-source processing.
6
Fetch via Jina
HTTP Request
Fetches each source URL via Jina Reader (r.jina.ai/{url}), which returns clean Markdown. Up to 6,000 characters of content. Jina handles pagination and noise stripping from raw HTML.
7
Fetch Succeeded?
IF
TRUE (content > 200 chars) → continue to Sonnet. FALSE (404, empty, or too short) → skip this source. Prevents sending blank content to Claude.
8
Build Sonnet Prompt
Code
Per-source extraction guidance injected into the prompt. release_notes → instruct Claude to expect production_mature with version evidence. github_repo → require release history signals before claiming production. sample_app → expect sample_only, warn Claude not to infer production from code examples alone. Also injects the source's source_role from the registry so Claude knows whether this is a full capability page or just a catalog/index.
9
Call Sonnet
HTTP Request → Anthropic
Sends the extraction prompt to Claude Sonnet. Returns a JSON array of capability objects per document. Each object: feature_name, support_maturity, evidence_summary, confidence_score, maturity_reason, capability_tag.
10
Parse Capabilities
Code
Parser safety caps applied here. If source_type === 'sample_app' and Claude returned maturity above sample_only → override and prepend [parser-cap] to maturity_reason. If source_type === 'github_repo' and maturity is production_mature without release signals → downgrade. Rows with valid capabilities are passed to the write step.
11
Any Capabilities Found?
IF
TRUE → write to Sheets. FALSE (Claude returned nothing useful for this source) → skip. This prevents appending empty rows.
12
Write to internal_capability_map
Google Sheets
Appends each validated capability row to the internal_capability_map tab. This tab is cleared and rebuilt each Monday: it's the single source of truth for what Ping can do, used by Competitor Intelligence for gap analysis.
info
Why internal_capability_map may appear empty
IPS clears the sheet at the start of every Monday run and rebuilds it from scratch. Outside of Monday runs the sheet will be empty: this is expected, not a bug. If it's empty on a Monday after 9 AM PST, check the execution_log to confirm the run completed and inspect the error_log for any fetch or parse failures.
